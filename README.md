# اندوخته

سامانهٔ مدیریت مالی. بک‌اند .NET 8 با معماری Clean Architecture و فرانت‌اند React 19 + Vite.

```
Andookhte/
├── src/
│   ├── Andookhte.Domain/          انتیتی‌ها و قواعد دامنه — بدون وابستگی بیرونی
│   ├── Andookhte.Application/     فیچرها (MediatR)، قراردادها، استثناها
│   ├── Andookhte.Infrastructure/  EF Core، هش رمز، JWT، ارسال کد یک‌بارمصرف
│   └── Andookhte.Api/             کنترلرها، میان‌افزارها، پیکربندی
└── andookhte-web/                 فرانت‌اند (README جداگانه دارد)
```

## راه‌اندازی از صفر

### ۱. مهاجرت دیتابیس

مهاجرت‌های قبلی با مدل جدید (کاربر، فضای کاری) ناسازگارند و حذف شده‌اند. یک بار این را اجرا کنید:

```bash
cd src/Andookhte.Api
rm -f AndookhteDb.db          # ویندوز: del AndookhteDb.db

dotnet ef migrations add InitialCreate --project ../Andookhte.Infrastructure --startup-project .
dotnet run
```

`dotnet run` هنگام بالا آمدن، `Database.Migrate()` را اجرا می‌کند و اسکیما ساخته می‌شود.

> اگر `dotnet ef` نصب نیست: `dotnet tool install --global dotnet-ef`

### ۲. کلید امضای JWT

در توسعه از `appsettings.Development.json` خوانده می‌شود. **در تولید حتماً از متغیر محیطی بدهید**، نه از فایل تنظیمات:

```bash
export Jwt__SigningKey="یک-رشتهٔ-تصادفی-حداقل-۳۲-نویسه"
```

برنامه اگر کلید تنظیم نشده یا کوتاه‌تر از ۳۲ نویسه باشد، عمداً بالا نمی‌آید.

### ۳. فرانت‌اند

```bash
cd andookhte-web
npm install
npm run dev
```

## معماری احراز هویت

**توکن دسترسی فقط هویت را حمل می‌کند، نه فضای کاری.** فضای کاری فعال در هر درخواست از هدر `X-Workspace-Id` خوانده و در برابر عضویت کاربر اعتبارسنجی می‌شود. نتیجه: تغییر نقش یک عضو **بلافاصله** اثر می‌کند و نیازی به صدور توکن تازه نیست.

**جداسازی داده با Global Query Filter انجام می‌شود، نه با `Where` دستی.** هر انتیتی که `IWorkspaceScoped` را پیاده کند، در `AppDbContext` فیلتر می‌خورد. دلیل این انتخاب ساده است: با `Where` دستی، یک بار فراموش‌کردن یعنی نشت دادهٔ یک کاربر به کاربر دیگر. با فیلتر سراسری، حالت پیش‌فرض «هیچ داده‌ای» است نه «همهٔ داده‌ها».

**چرخش توکن تمدید.** هر بار تمدید، توکن قبلی باطل و به توکن جدید زنجیر می‌شود. اگر توکن باطل‌شده دوباره استفاده شود (نشانهٔ سرقت)، همهٔ نشست‌های آن کاربر باطل می‌شوند.

**هیچ توکن یا کدی به‌صورت خام ذخیره نمی‌شود** — فقط هش SHA-256. رمز عبور با PBKDF2-HMAC-SHA256 و ۲۱۰٬۰۰۰ تکرار هش می‌شود و تعداد تکرار داخل خود رشته ذخیره می‌گردد تا در آینده بدون بی‌اعتبارکردن رمزهای قدیمی قابل افزایش باشد.

### نقش‌ها

نقش‌ها صعودی‌اند تا مقایسهٔ سطح دسترسی ساده باشد:

| نقش | مقدار | دسترسی |
|---|---|---|
| بیننده | ۱ | فقط مشاهده |
| حسابدار | ۲ | حساب‌ها و تراکنش‌ها |
| مدیر | ۳ | مدیریت اعضا |
| مالک | ۴ | همه‌چیز |

قواعدی که در کد اعمال شده‌اند: کسی نمی‌تواند نقشی **بالاتر از نقش خودش** بدهد، نقش مالک از مسیر عادی قابل واگذاری نیست، و کاربر نمی‌تواند نقش یا عضویت خودش را تغییر دهد.

## قواعد مالی

**اثر مالی در یک نقطه نوشته شده.** کلاس `BalanceEffect` تنها جایی است که موجودی حساب تغییر می‌کند. ثبت یک بار `Apply` می‌زند، حذف یک بار `Revert`، و ویرایش ابتدا `Revert` با مقادیر قدیمی و سپس `Apply` با مقادیر جدید. اگر هرکدام نسخهٔ خودش را داشت، دیر یا زود واگرا می‌شدند — دقیقاً همان اتفاقی که در نسخهٔ اول افتاد و موجودی دو بار کسر می‌شد.

**حذف تراکنش نرم است ولی اثر مالی واقعاً برمی‌گردد.** در غیر این صورت مجموع موجودی با مجموع تراکنش‌های قابل مشاهده نمی‌خواند.

**حساب دارای تراکنش قابل حذف نیست.** حذفش تاریخچه را بی‌معنا می‌کند: تراکنش‌ها به حسابی اشاره می‌کنند که دیگر نیست. به‌جای حذف آبشاری، عملیات با پیام روشن رد می‌شود.

**موجودی از فرم ویرایش حساب تغییر نمی‌کند.** موجودی حاصل تراکنش‌هاست؛ تغییر دستی آن باعث می‌شود مجموع تراکنش‌ها با موجودی نخواند.

## پیامک

تا وقتی `Sms:ApiKey` خالی باشد، `LoggingOtpSender` فعال است و کد را در لاگ می‌نویسد (و در محیط توسعه در پاسخ API هم برمی‌گرداند). با تنظیم کلید، `KavenegarOtpSender` جایگزین می‌شود و کد هرگز در پاسخ برنمی‌گردد:

```json
"Sms": {
  "ApiKey": "کلید پنل",
  "Template": "نام الگوی تأییدشده",
  "Sender": "شمارهٔ فرستنده"
}
```

ارسال با الگو (سرویس lookup) برای پیامک احراز هویت الزامی است؛ بدون آن پنل پیام را رد می‌کند. گیرندهٔ ایمیلی پشتیبانی نمی‌شود و به یک پیاده‌سازی SMTP جداگانه نیاز دارد.

## باگ‌هایی که در این مرحله رفع شدند

**محاسبهٔ دوبارهٔ موجودی.** در `CreateTransactionCommandHandler` قدیمی، موجودی حساب دو بار اعمال می‌شد: یک بار در بلوک `switch` اولیه و بار دوم در بلوک‌های «بررسی وجود حساب». هر هزینه دو برابر کسر و هر انتقال دو برابر جابه‌جا می‌شد. اکنون هر شاخه دقیقاً یک بار موجودی را تغییر می‌دهد.

**`EnsureCreated` به‌جای `Migrate`.** با `EnsureCreated()` مهاجرت‌ها هرگز اجرا نمی‌شوند و اسکیمای دیتابیس از مدل عقب می‌ماند. جایگزین شد با `MigrateAsync()`.

**کوئری‌های همگام.** هندلرها از `ToList()` روی `IQueryable` استفاده می‌کردند که همچنان به دیتابیس می‌زند و فقط نخ را بلاک می‌کند. همه به `ToListAsync()` تبدیل شدند.

## کارهای باقی‌مانده

- **کلید پنل پیامک.** بدون `Sms:ApiKey`، ورود با پیامک فقط در محیط توسعه کار می‌کند.
- **تحویل ایمیل.** بازیابی رمز با ایمیل کد صادر می‌کند ولی راهی برای رساندنش نیست؛ نیاز به پیاده‌سازی SMTP دارد.
- **محل نگهداری توکن در مرورگر.** توکن‌ها در `localStorage` ذخیره می‌شوند که در برابر XSS آسیب‌پذیر است. امن‌تر: کوکی `httpOnly` که نیازمند تغییر سمت سرور و محافظت CSRF است.
- **تست.** هیچ تستی نوشته نشده — نه واحد، نه یکپارچگی. با حجم منطقی که در `BalanceEffect` و فیلترهای دسترسی هست، این بزرگ‌ترین ریسک باقی‌مانده است.
- **SQLite در تولید.** برای چندکاربره مناسب نیست؛ نوشتن هم‌زمان کل دیتابیس را قفل می‌کند. ضمناً `decimal` را به‌صورت `TEXT` ذخیره می‌کند، پس هر مقایسه یا `Sum` روی مبلغ در سطح SQL نادرست است — به همین دلیل مرتب‌سازی حساب‌ها در حافظه انجام می‌شود.
